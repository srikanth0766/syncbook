Syncbook 

Problem statement
Syncbook is a cloud-based Central Reservation System (CRS) used by hotels to manage room inventory, pricing, availability, and reservations across multiple booking channels such as hotel websites, online travel agencies, travel agents, and call centers. It acts as a central hub that keeps booking information synchronized between these systems and helps hotels distribute their rooms efficiently.

Functional requirements
* Manage multiple hotels and their room inventory.
* Run multiple instances of the same booking website to simulate different booking channels (Booking.com, Agoda, OYO, etc.).
* Allow users to view available rooms and make bookings, update and delete from any booking channel.
* If one user makes a booking in one channel he can only delete in that channel.
* Maintain a central inventory of room availability.
* Update the central inventory whenever a booking is made from any channel.
* Synchronize updated room availability across all booking channel instances.
* Handle a booking channel going offline without affecting the other channels.
* Synchronize an offline channel with the latest data when it comes back online.
* Store and manage booking details centrally.
* Support simple data transformation for different external systems/formats (such as PMS or CRM).

Non functional requirements
* Availability – The system should continue functioning even if one booking channel goes offline.
* Reliability – Bookings and inventory updates should not be lost.
* Data Consistency – Room availability should eventually remain consistent across all booking channels.
* Fault Tolerance – Failure of one channel should not affect other channels or the central platform.
* Scalability – The system should support adding more hotels and booking channel instances easily.
* Performance – Booking and inventory updates should be processed with minimal delay.
* Recoverability – Offline channels should receive missed updates when they come back online.
* Maintainability – New booking channels or external integrations should be easy to add.
* Usability – The booking website and management platform should have a simple and understandable interface.
* Security – Basic authentication and validation should protect booking and hotel data.

Success criteria
* A user can successfully make a booking from any booking channel.
* The central inventory is updated correctly after every booking.
* All active booking channels receive the updated inventory.
* The system prevents overbooking.
* If one channel goes offline, other channels continue functioning.
* When the offline channel comes back online, it receives the latest inventory data.
* Booking data is stored correctly in the central system.
* The complete system can be run and demonstrated using Docker containers.
User stories
* As a customer, I want to view available hotels and rooms on a booking channel so that I can choose a room.
* As a customer, I want to make a booking through any booking channel so that I can reserve a room, or even cancel a reservation.
* As the central platform, I want to maintain a central record of bookings and room inventory so that there is a single source of truth.
* As the central platform, I want to update the central inventory when a booking is made from any channel.
* As the central platform, I want to synchronize inventory updates across all active booking channels so that they display the latest room availability.
* As the central platform, I want to handle an offline booking channel and synchronize its data when it comes back online so that temporary failures do not cause permanent data inconsistencies.
* As the central platform, I want to transform booking data into different formats when communicating with external systems so that different systems can be integrated later.

FULL RESYNCHRONIZATION
----------------------

If the channel cannot recover using pending messages:

Channel
        ↓
POST /channels/{channel_id}/recover
        ↓
SyncBook
        ↓
Send Latest Hotel, Room Type and Booking Data
        ↓
Channel Rebuilds Local Database
        ↓
Resume Normal Synchronization

Failure & Recovery Design
FAILURE AND RECOVERY DESIGN
===========================


1. BOOKING CHANNEL FAILURE
--------------------------

Channel Goes Offline
        ↓
Other Channels Continue Working
        ↓
Messages Continue to be Stored
in the Channel-Specific Queue
        ↓
Channel Comes Back Online
        ↓
Consume Pending Messages
        ↓
Update Local Database

If recovery fails:
        ↓
Request Full Resynchronization
from SyncBook


2. SYNCBOOK INSTANCE FAILURE
----------------------------

SyncBook Instance Fails
        ↓
Other SyncBook Instance
Continues Processing
        ↓
RabbitMQ Retains Unprocessed Messages
        ↓
Failed Instance Restarts
        ↓
Reconnects to System


3. RABBITMQ MESSAGE FAILURE
---------------------------

Message Processing Fails
        ↓
Retry Processing
        ↓
Still Fails
        ↓
Move to Dead Letter Queue
        ↓
Retry / Manual Recovery


4. HOTEL/PMS FAILURE
--------------------

Hotel/PMS Becomes Unavailable
        ↓
SyncBook Cannot Complete Request
        ↓
Booking Request Remains
Pending / Retried
        ↓
Hotel/PMS Recovers
        ↓
SyncBook Retries Request
        ↓
Booking Processing Continues


5. DATABASE FAILURE
-------------------

Service Database Becomes Unavailable
        ↓
Service Cannot Process New Operations
        ↓
Other Independent Services
Continue Working
        ↓
Database Recovers
        ↓
Service Resumes Processing


6. DATA SYNCHRONIZATION FAILURE
-------------------------------

Channel Misses Updates
        ↓
Consume Pending Queue Messages

If Messages Are Missing:
        ↓
Request Full Resynchronization
        ↓
SyncBook Sends Latest Data
        ↓
Channel Rebuilds Local State


RECOVERY PRINCIPLES
-------------------

- Services operate independently
- One channel failure does not affect others
- Multiple SyncBook instances prevent single point of failure
- RabbitMQ prevents temporary message loss
- Dead Letter Queues store failed messages
- Hotel/PMS remains the source of truth
- Full resynchronization fixes inconsistent channel data
Authentication & Security Design
AUTHENTICATION AND SECURITY DESIGN
==================================


1. AUTHENTICATION
-----------------

Customer
    ↓
Login / Register
    ↓
Authentication Service
    ↓
Validate Credentials
    ↓
Generate JWT Token
    ↓
Return Token


For protected requests:

Customer
    ↓
Send JWT Token
    ↓
Booking Channel Backend
    ↓
Validate Token
    ↓
Allow / Deny Request


2. AUTHORIZATION
----------------

CUSTOMER
- Create booking
- View own booking
- Update own booking
- Cancel own booking


SYSTEM / SERVICE
- Access internal APIs
- Publish RabbitMQ messages
- Consume RabbitMQ messages


3. PASSWORD SECURITY
--------------------

User Password
    ↓
Hash using bcrypt
    ↓
Store Password Hash

Passwords are never stored in plain text.


4. API SECURITY
---------------

- JWT authentication for protected APIs
- Input validation using Pydantic
- Validate request data
- Validate booking ownership
- Reject invalid or unauthorized requests


5. INTERNAL SERVICE SECURITY
-----------------------------

Booking Channel
      ↓
   SyncBook

Hotel/PMS
      ↓
   SyncBook

Internal communication is authenticated using
service credentials / API keys.


6. DATABASE SECURITY
--------------------

- Each service accesses only its own database
- No service directly accesses another service's database
- Database credentials are stored in environment variables
- Sensitive data is not hardcoded


7. MESSAGE QUEUE SECURITY
-------------------------

- RabbitMQ requires authentication
- Each service uses separate credentials
- Services only access required queues
- Message data is validated before processing


SECURITY PRINCIPLE
------------------

Customer
    ↓
JWT Authentication
    ↓
Booking Channel

Services
    ↓
Service Authentication
    ↓
Internal APIs / RabbitMQ

Each Component
    ↓
Accesses Only Its Own Database
